## Release 0.40

- The program is discontinued (user decision of 2026-11-12): this is the last version. Its successor is the new Random & Everywhere Companion (experimental build of the R&E team, repository KeKKERUUU/RandomEverywhereInstaller). At every start a notice says that the program will not be updated any more and asks what to do: uninstall this program and install the new Companion, or keep this program and start the new Companion (not now closes the notice; the Discord discussion of the experimental Companion, https://discord.com/channels/1285277168103981197/1562848679142887484, opens from it). The same notice opens from the button The new Companion... of the Updates tab. Nothing is downloaded before a click. The setup of the newest test build of the successor is downloaded from the build host of the R&E team (its index `test/latest.json` gives the path, size and sha256; when the index cannot be read the build 5a3ac93e2a, known when this version was made, is used; size and sha256 checked), started with its own wizard (it asks for the administrator right) and waited for; only when it ended well this program starts the new Companion and closes. Uninstalling runs the silent uninstaller of this program (settings, voices and packs stay in the folder, no `/removedata`); keeping removes this program from the EXE.xml of the simulators so that it does not start next to the new one (the Service tab checkbox turns it on again). If the new Companion is already installed it is started without a download; a failed download or setup changes nothing and offers the download page. A copy that was not installed by the setup cannot be uninstalled from here (the button is off).
- The updates of the mission and of the voice packs no longer go through this program: the published mission and packs are not read any more (the 30 minute watch that fed the mission notice of a new build is gone, so the variables `L:HMC_MISSION_LATEST_MAJOR` and `L:HMC_MISSION_LATEST_MINOR` stay at 0), the mission file box and the choices of the Updates tab are switched off, and the check looks only for a newer program. The way to a newer version of the program stays open: a release with a higher version and the asset `HPGMissionCompanionSetup.exe` is still offered by the Updates tab.
- Documents: README.md. Runtime in the simulator pending.

## Release 0.31

- Port 5997 stayed busy after an update (report of the author, 2026-10-17, update 0.29 to 0.30: "Port 5997 is busy: PID 12056 uses it", the owner no longer existed; closing and opening the program again cleared it). Cause: the socket of the service could be inherited by the programs this one starts. The old program stopped the service and ended, but the setup that it started with Process.Start (UseShellExecute false) and the new program that the setup started the same way kept the inherited copy of the listening socket, so the port stayed in use until the new program was closed. The listening socket and the accepted connections are now not inheritable (Server.NoInherit, SetHandleInformation), and the setup starts the program through the shell (UseShellExecute true), which passes no handle: the update of a program that still has the defect (0.30 and older) is protected too, the setup itself ends right after starting the program and the program retries the port for 4 seconds.
- Command line `--port-leak-test <report>`: starts a service, a program that outlives it, and checks that the port is free after the service stops (an ordinary listener leaks into the child: the report says BUSY; the Server does not).

Program: latest GitHub release of this repository (asset HPGMissionCompanionSetup.exe). Releases compare as two integers (169.9 comes before 169.45; the program 0.10 after 0.9).
- An automatic check only reads and tells: a balloon of the notification area (and the Tools tab log) says what is newer, and a click on it opens the Tools tab and asks the question; nothing is downloaded without it. If something is newer you are asked once. Yes: the mission file is downloaded and checked (size, sha256 when the release gives it, the file ends with its closing brace, its title is the release announced), the installed file is copied to backups\mission (never inside the Community folder: the index tool would list a copy as a mission), replaced through a .part file, and the mission index is updated; then the program: the setup is downloaded (size and sha256), the program closes and the setup (/S /dir=this folder, no shortcuts when this folder was not installed by the setup) installs and starts it again. The mission always comes first; an error stops the sequence and keeps what was done.
- The mission file to replace is chosen from the copies found (the ones with a release number first; an original file without a release number is replaced only after the question says so) or with Browse; the choice is kept (setting MissionFile). Setting MissionUrl is the fallback link.
- Release notes in the update question and in a button: the question of the update is a window with the notes of what is newer (the body of the GitHub release: for the mission the user changelog of the builds since the previous release, for the program the changelog of the versions), scrollable, with "Download and install" and "Not now" (the default answer is Not now). A mission taken from the Google Drive link has no notes and the window says so. The new button "What's new..." of the Tools tab shows the notes of the latest published mission and program also when nothing is newer.
- Command line for checks without the window: --check-updates <report> [--community <dir>] [--index-file <file>] [--mission-url <url>] [--github-mission <api url>] [--github-app <api url>] and --test-replace <installed> --with <file> --backup <dir>.
